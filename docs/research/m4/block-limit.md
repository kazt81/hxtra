# The 8-block limit

Where the HX Stomp's limit of 8 blocks per preset lives, and why a 9th block fails. Researched 2026-11-06 and parked; the code from that work is not in the tree (see [What was tried](#what-was-tried)). Status tags as in [conventions.md](../conventions.md).

## Block layout

- **The grid** [verified offline]: blocks sit in 8 columns on two rows, as on the Helix: block IDs 1..8 are path A, 11..18 path B (`0x28e07328`); the UI slot model `0x2812c590` and the DSP model's 16 records cover both rows. No ID exists for a 9th column. Block IDs and records: [dsp-cost.md](dsp-cost.md); the split and merge: [split-routing.md](split-routing.md).
- **One block per column on screen** [verified offline, then on unit]: the Edit view has 8 block widgets; for each column `0x28dc1a86` shows the path-B block if `0x28dd2a74` finds one, else path A's. On the unit, a preset with a path-A and a path-B block in one column (`SS5-SharedKey7.hlx`, imported through HX Edit) shows only the path-B block on the HX Stomp, while HX Edit shows both.
- **Split/Merge normalisation** [verified offline, matches the unit]: the slot-model refresh `0x28dd2b48` walks all 16 slots; for every path-B block it moves the Split before that block's column (`0x28e03ddc`, from `0x28dd2c8a`) and the Merge after it (`0x28e041e0`, from `0x28dd2c70`) in the DSP model. Its slot-model positions: Split `+0x21` (ID 10's column), Merge `+0x22` (IDs 9 and 19), 7 when absent. On the unit, a path-B block placed left of the Split came back with the Split moved before it.
- **Split position** [verified on unit]: the stock UI stops the Split after column 7 (path B gets column 8 at least). A file with the Split at `@position` 8 and no path-B blocks loads as a serial chain without a Split.
- **Path-B output** [verified on unit]: with the Merge moved down (`@topology0` `"SAB"`), path B ends in `HelixStomp_AppDSPFlowOutputSend`, which only goes to Send L/R.

## The cap is a count, enforced twice

- **HX Edit drops a 9th block** [verified on unit, stock 3.80 with HX Edit 3.71]: presets with a 9th block (`"block8"`) lose it on import, whatever its place; a shared column within 8 blocks survives. Entry 0 contains no `.hlx` keys (`@position`, `@topology0`, model names), so HX Edit converts the file before upload, and that conversion is outside the firmware.
- **The HX Stomp refuses it too** [verified on unit]: with 8 blocks and column 7 left empty (`SS5-SharedKey7.hlx`), the cursor stops on the empty cell, but choosing a model adds nothing, and HX Edit greys out every model for that cell.
- **The free-slot counter** [verified offline]: `preset[0xac0]` is the number of free block slots. It is 8 after the preset init (`movs r3,#8` at `0x28df5cf6`) and after a clear (`0x28df4b40`), `8 - [0xab8]` at `0x28df85ee`, goes down by 1 when a block is added (`0x28df6c94`, `0x28df732a`) and up by 1 when one is removed (`0x28df6bce`, `0x28df73c0`, `0x28df7fee`, `0x28df8f10`), and `0x28df4030` branches away at 0. It is also computed from other values at `0x28df4172`, `0x28df4192`, `0x28df6eec`, `0x28df7410`.
- **What the counter covers** [verified on unit, block probe]: `[0xab8]` counts the serial blocks before the Split, and the counter (with `[0xabc]`, [hypothesis] the blocks after the Merge) covers only the serial part. Probe readings `[0xac0]/[0xab8]/[0xabc]` with the counter's 8s at 9: empty preset `9/0/0`; SplitTest (7 blocks before the Split, 1 on path B) `2/7/0`; SS5 (5 before the Split, 1 on A and 2 on B after it) `4/5/0`. [hypothesis] the preset keeps its blocks in a fixed array, path A filling from the front and path B from the back, since the DSP-model code indexes path B from `8 - [0xabc]` (`0x28e0940e`, `0x28e09606`, `0x28e0c178`, `0x28e0c1ec`, `0x28e0e132`).
- **Three slot tables** [verified offline]: the per-path struct holds three tables of 8 slots of `0x14` bytes, bit 2 of word 4 in use: `+0x80c..0x898`, `+0x8b0..0x93c`, `+0x954..0x9e0`, counted into three totals at `0x28df3f1c`. [hypothesis] serial, parallel path A, parallel path B: 24 slots, but the block objects below run out first.
- **Can-add check** [verified offline]: `0x28e005bc` (called from the request validator at `0x28e07e94`) runs the per-type rules `0x28dfa9a4` (at most 2 of each heavy type, counts at `preset[0xa90..0xa98]`; see [AMP_LIMIT.md](../AMP_LIMIT.md)) and then the DSP fit `0x28dfae0c` (the 90% limit, [dsp-cost.md](dsp-cost.md)).

## Why a 9th block fails: the block objects

- **The add fails in the allocator** [verified on unit, probe images with the counter at 9; the spies take function entries with `p.own_entry`]: adding a block on the HX Stomp goes through the request dispatcher `0x28e0fc14` to `0x28e02ee0`, which validates at `0x28e03024` (validator `0x28e07dc4`: result 1, error 0 for the add into SS5's empty column 7), carries it out with `0x28e05298` (0) and then calls `0x28e0c124` (→ `0x28e0bde4`), from which `0x28e02ee0` returns **-19** (`-0x13`, the code the UI's "DSP Full!" path also returns). Under it, the block-object allocator `0x28df4d24` was called with kind 1 (an effect) and found no object (`0x28df5438` then returns -19). The path struct's objects read `5/5/3/9`: the 5 below `preset[0xac4]` in use, 3 of the 4 above it in use, one free. A model change on an existing block goes the same way and returns 0. The UI's `0x28e035a0`/`0x28e03790` and `0x28e03884`/`0x28e036ac` are not on this path.
- **Nine block objects a path** [verified offline]: the per-path struct (`0x6484` bytes, at `[dsp + 0x43fc] + 0x6484 * n`, `n` from the path, `0x28e093e2`) ends in 9 objects of `0x9f4` at `+0xaf0` (9 * `0x9f4` + `0xaf0` = `0x6484`), one per block. The struct is per DSP path, not per stored preset.
- **The objects are typed** [verified offline]: objects 0..4 (`+0xaf0`) are the pool most kinds take (`0x28df4d36`, up to `preset[0xac4]` = 5, set by `0x28dffc60` through the init `0x28df5ccc`); objects 5..7 (`+0x3cb4`, `+0x46a8`, `+0x509c`) are taken only by kinds 0x10..0x12 and 0x21 (`0x28df4da2..`); object 8 (`+0x5a90`, in use bit at `preset + 0x5ab4`) only by kind 0x16 (`0x28df52c4`, `0x28df54d8`), [hypothesis] the Looper.
- **So**: a path holds at most 9 blocks of storage, and fewer of any one kind. More than 9 needs a larger path struct, and `0x6484` is used as the stride throughout the code (`0x6484 * n`); this was not attempted.

## Open questions

- **Five general objects against eight effects**: `SS5-SharedKey7.hlx` holds a 3-Band Comp, an amp, a cab, a Graphic EQ, a tremolo, a chorus, a reverb and a delay, and the probe read 5 general objects and 3 of objects 5..7 in use. If only amp/cab-type kinds took objects 5..7, the six blocks that are neither amp nor cab would not fit in 5. Either the reverb or delay kind is among 0x10..0x12 and 0x21, or another kind can take objects 5..7. Not checked: the kind bytes of SS5's blocks, and whether a stock preset of 8 effects with no amp or cab loads.
- **An allocator fallback** [hypothesis, not tried]: short of a larger path struct, the allocator could lend a free object of another type (5..8) to a kind whose pool is full, which would allow a 9th block only while the preset leaves a typed object unused (as SS5's free object 8). The boot freeze below suggests some kinds depend on finding their reserved objects free.
- Whether a 9th block, once stored, would show on screen (8 block widgets) or survive HX Edit (it drops `block8` on import) was never reached.

## What was tried

All on the unit by RAM run, stock 3.80 + HX Edit 3.71. The code lived in commit `a2ef38d` ("Max blocks research"), which is on no branch: `tools/features/max_blocks.py` and `tests/test_max_blocks.py` (`HX_MAX_BLOCKS=9`), `tools/features/block_probe.py` and `src/m4/block_probe.s` (`HX_BLOCK_PROBE=1`; it owned `0x28df4d24` and `0x28e02ee0` and drew in the Edit view's top right corner, so it conflicted with the DSP meter), `tests/test_block_probe.py`, and the `.hlx` test presets `SplitTest` (exported from HX Edit) and `SS1-Split8`, `SS2-BLeft`, `SS3-Shared9`, `SS3b-Hidden9`, `SS4-Serial11`, `SS4a-Serial11`, `SS5-SharedKey7` made from it.

- **Max Blocks 9** (`HX_MAX_BLOCKS=9`, MD5 `3ccd4ec3bb6398ff65a6d9692b1ec578`: the counter's three 8s, at `0x28df5cf6`, `0x28df4b40` and `0x28df85ee`, set to 9) [verified on unit]: no change. SS5's empty column takes no block, and an emptied preset still stops at 8.
- **Block probe** (`HX_BLOCK_PROBE=1 HX_MAX_BLOCKS=9`, MD5 `37bb068ecdca823337789d69431df01d`) [verified on unit]: the counter readings above; the 9 took effect without allowing a 9th block.
- **Allocator and request spies** (probe images `fc57d4bc..`, `6ab31f23..`, `965bf942..`, `e70b2f99..`, `f3113478..`, `7ea00091..`) [verified on unit]: the -19 from the allocator, above.
- **Pool limit 9** (`HX_MAX_BLOCKS=9` plus `mov.w r9,#9` at `0x28dffc60`, MD5 `01534c2698356684bea8f5eaceed0775`) [verified on unit]: **froze during boot**. [hypothesis] pool kinds then took objects 5..8 while loading, and the kinds reserved for them failed. The patch was dropped.
